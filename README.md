# 净影 · 电脑版（Windows）

一个不依赖第三方解析服务、单条解析无需登录的抖音无水印下载器（桌面版）。
粘贴抖音分享口令/链接 → 程序驱动本地 Chromium 打开抖音官方网页 → 读取网页自己加载出的
作品数据与播放地址 → 下载到本地目录。所有解析都在本机完成，功能对齐 Android 版
[净影 v1.3.0](https://github.com/jingying)。

> 受 [MediaCrawler](https://github.com/NanmiCoder/MediaCrawler) 的抖音详情接口与媒体下载
> 思路启发。本项目是独立实现，不包含 MediaCrawler 源码，也不依赖其运行环境。

---

## 两种使用方式

**方式一：免安装 exe（推荐）**

解压发行 zip（文件名由发版脚本按版本自动生成：`净影-PC-v<版本>-win64.zip`，
版本号见 `config.py` 的 `APP_VERSION` 或 `CHANGELOG.md`），双击 `JingYingPC.exe`
即可打开图形界面，无需安装 Python。首次使用前请确认电脑上有 Google Chrome
或 Microsoft Edge。

**方式二：Python 源码运行**

见下文「安装与运行」；适合二次开发。命令行自检：

```powershell
python app.py --selftest
```

会依次测试：链接解析 → 真实抖音作品抓取 → 音乐下载 → 完整下载（视频+音乐+目录结构）。

## 版本与发版

版本唯一真源是 `config.py` 的 `APP_VERSION`（语义化版本），窗口标题、exe 版本资源、
便携目录 / zip 名、CHANGELOG、git tag 全部由它派生，**不要在其他地方手写版本号**。

| 位置 | 来源 |
|---|---|
| 窗口标题 | `config.window_title()`；发行包额外带构建短 sha |
| exe 属性 | `file_version_info.txt`，每次发版按版本重新生成 |
| 启动日志 | `app.log` 的 `version=... build=...` 行 |
| 产物名 | `净影-便携版-v<版本>/`、`净影-PC-v<版本>-win64.zip` |
| 更新日志 | `CHANGELOG.md` |
| git tag / Release | `v<版本>` |

发版流程（改完代码、跑完测试后）：

1. 按语义化版本修改 `config.APP_VERSION`；在 `CHANGELOG.md` 补该版本段落
   （没写时脚本会从 git log 自动补一节）。
2. `python build_release.py`：依次跑全量测试、PyInstaller 构建、组装带登录态的
   便携目录、压缩、CRC 校验，产物默认输出到桌面。
   - 干净包（不带 Cookie / 通讯录 / 历史）加 `--no-data`；
   - 复用已有构建加 `--skip-build`；CI 已跑测试加 `--skip-tests`；
   - 同名产物默认不覆盖，`--force` 会把旧产物改名备份后重建。
3. `git tag -a v<版本> -m '...'`，推送后在 GitHub 建 Release 并挂上对应 zip。

> 便携包里的 `VERSION.txt` / `build_sha.txt` 与窗口标题括号里的短 sha，
> 用于在反馈问题时定位具体构建。

## 功能（对齐 Android v1.3.0）

- **无水印视频（原画质）**：去水印是把 `playwm` 换成 `play` 的地址变体替换，不重编码、
  不掉画质；清晰度则在 `bit_rate` 阶梯里挑**分辨率最大的那条**（通常是 2048/2160 的
  H.265），同一分辨率再比「是否完整 mp4 → 码率 → 体积 → H.265」——码率必须排在体积
  前面，因为部分档位不带 `data_size`，按体积比会把高分档当成 0，反而选中低码率档。
  结果卡片与下载日志都会显示实际选中的清晰度，例如「原画 2160p · H.265」。

  短链（`v.douyin.com/...`）解析出作品 ID 后会回到桌面作品页再取详情，避免停在 H5
  分享页只拿到 720p 兜底地址；万一只拿到兜底地址，画质会标成「兜底地址（未取到画质
  阶梯）」并写 `app.log` 警告，不会假装是原画。

  图集受网页接口限制：`url_list` 是签名绑定的 `q75.webp` 压缩图（改参数会 403），
  `download_url_list` 同尺寸且带水印，所以图集取的是无水印的 `url_list`。
- **作品信息**：标题、作者、抖音号、封面、时长、点赞/评论/收藏数据。
- **图集作品**：按顺序保存整组图片。
- **主页批量下载**：粘贴创作者主页链接，自动滚动加载，一键下载全部作品
  （视频 + 图集 + 背景音乐），支持失败计数。
- **可选 tar 打包**：主界面「WebDAV 备份」卡片可勾选「下载完成后打包成 tar」，
  勾选后每个作品下载完打成一个 `<作品id>.tar` 并删除散文件，WebDAV 也只上传
  这个 tar；播放时按需解包，首次打开可能稍慢（开关旁有提示）。默认关闭，仍是
  一个作品一个文件夹。
- **通讯录同步**：把作者主页「加入通讯录」，点「全部同步」下载各作者全部作品；
  支持失败重试、删除。当前版本打开程序**不会**自动开始同步（`_auto_sync` 尚未接入
  启动流程），需要手动点「全部同步」。
- **三块独立窗口**：通讯录、传输、最近保存各自一个窗口，从主界面按钮打开
  （按钮上带作者数/作品数）；关闭只是隐藏，后台任务仍在继续，再次打开内容还在。
- **同步日志**：主界面「查看日志」打开独立窗口，记录整体「开始同步 / 同步结束」、
  每位作者的「用 账号N 开始同步 作者」以及完成行
  「[时间] 使用 账号N 同步了 作者 的 X 个作品」；不掺杂下载失败、网络重试等噪声
  （那些在 `app.log`）。窗口开着时每 1.2 秒自动刷新。
- **下载日志**：主界面「下载日志」打开独立窗口，记录「用 账号N 打开了 作者，找到了
  X 个作品」，每个作品一条「开始下载」和一条「下载完成（还剩 N 个没下完 / 已全部
  下完）」，失败也会记一条「下载失败」；同步和批量下载都会记录，窗口开着时自动刷新。
- **登录五个号 + 多账号并发同步**：右上角账号下拉选择「账号 1」到「账号 5」，逐个
  扫码登录。同步时每个已登录账号各占一个浏览器，同时抓取不同作者——多个账号并行
  能明显加快整轮同步；同一账号同一时刻只开一个浏览器（各账号用独立的浏览器配置
  目录），避免 Chromium 的配置锁冲突。只登录一个账号时就是单账号串行。
  主页作品列表需要登录，Cookie 保存在本机，之后解析自动复用。
  程序不读取、不上传账号密码。

## 保存目录（2026-11-09 起：一个作品一个文件夹）

```text
净影/作者名_抖音号/<作品id>/
      ├─ 视频.mp4        （视频作品）
      ├─ 图片_01.jpg …   （图集作品，按顺序）
      ├─ 动图_01.mp4     （实况图对应的动图）
      ├─ 音乐.mp3        （作品自带背景音乐）
      └─ 文案.txt        （作者、抖音号、发布时间、作品链接、完整文案）
```

- 作品文件夹直接用**作品 id** 命名，视频 / 图集图片 / 实况动图 / 背景音乐 / 文案
  全部放在同一个文件夹里，不再打 tar，也不再单独建 `Music/`；
- `净影` 放在下载根目录下，和 `Videos`、`Music`、`作者资料` 平级：
  便携版是 `JingYingPC/downloads/净影/…`，源码运行是 `C:\Users\<你>\净影\…`；
- 旧数据照常识别、不会重复下载：`Videos/作者/<作品id>.tar`（2026-11-08 那批）和
  更早的 `Videos/作者/作者_文案_时间/`；
- WebDAV 上传的相对路径就是 `净影/作者/作品id/文件`；「上传后清理本地」会把
  `净影` 下的媒体文件一起清掉（文案保留）。

## 安装与运行

1. 安装 Python 3.10+（Windows，安装时勾选「Add Python to PATH」）。
2. 双击 **`安装依赖.bat`**（等价于 `pip install -r requirements.txt`）。
3. 准备浏览器（自动查找，按顺序）：

   - 环境变量 `JINGYING_CHROME` 指定的 Chrome/Edge；
   - 程序目录 `tools/chromium/chrome-win/chrome.exe`（便携版）；
   - 系统安装的 Google Chrome / Microsoft Edge。

   便携版会先做一次完整性检查：同目录缺少 `chrome_crashpad_handler.exe` 时直接跳过
   （这种残缺包启动时会报 `crash server failed to launch, self-terminating` 立刻退出，
   表现为所有解析都失败），自动退到系统 Chrome / Edge。

   如自动找不到，设置环境变量指向你自己的浏览器：

   ```powershell
   set JINGYING_CHROME=C:\Program Files\Google\Chrome\Application\chrome.exe
   ```

4. 双击 **`启动净影.bat`**（等价于 `python app.py`）。

> 数据目录：默认在程序文件夹同级的 `JingYingData`（便携模式），重新解压发行包
> 或重建 `dist` 都不会清空；该位置不可写时回退到 `%LOCALAPPDATA%\JingYing`。
> 旧版 exe 同目录 `data/` 和 `%LOCALAPPDATA%\JingYing` 的文件会自动迁移。
> 下载目录可用 `JINGYING_DOWNLOAD_BASE` / `JINGYING_MUSIC_BASE` 覆盖。

## 使用流程

1. 复制抖音作品链接或作者主页链接（`https://www.douyin.com/…`）。
2. 粘贴到输入框，点「开始解析」。
3. 作品：显示封面/标题/作者，点「保存视频 + 音乐」。
4. 主页：显示「视频 N · 图集 M」，点「下载全部（视频 + 图集 + 音乐）」；或点「加入通讯录」。
5. 主页作品列表需要登录：右上角账号下拉选择账号 1～账号 5，点「登录抖音」，
   浏览器窗口会自动弹出并置前；扫码/手机号登录完成后，回到程序点「我已完成登录」。
   所有已登录账号会在通讯录同步时按作者轮流使用。
6. 通讯录里的作者每次打开程序会自动同步全部作品。

> 本版本已移除内置播放器（「观看已下载」入口与 `player.py` / `player_entry.py` 代码
> 一并删除）：下载产物是作品文件夹（或勾选开关后的 tar 包），直接在资源管理器里用
> 系统播放器打开即可。

## 项目结构

```
jingying-pc/
├─ app.py            # 主窗口骨架：单条解析、批量、历史列表、登录、UI 搭建
├─ windows.py        # 通讯录 / 最近保存 / 传输 / 同步日志 / 下载日志 独立窗口
├─ sync_log.py       # 「查看日志」专用记录（仅账号/作者/作品数，落盘 sync_log.txt）
├─ download_log.py   # 「下载日志」专用记录（作者/作品/剩余数，落盘 download_log.txt）
├─ line_log.py       # 上面两个日志共用的「后台攒批写盘 + 读取裁剪」
├─ archive.py        # 作品归档：打 tar、读成员（历史列表读取旧 tar 的文案与图片清单）
├─ webdav_panel.py   # WebDAV 上传/进度/上传记录/上传后清理（WebdavMixin）
├─ contacts_sync.py  # 通讯录同步状态机、失败重试、多账号并发 worker 池（ContactsSyncMixin）
├─ workers.py        # 后台任务线程 Worker（各 mixin 共用）
├─ parser.py         # Playwright 驱动 Chromium 抓详情/主页 + 登录（按账号配置目录分锁，可并发）
├─ models.py         # aweme JSON → MediaInfo（含音乐、抖音号）
├─ links.py          # 链接/短链/作品 ID/sec_uid 解析
├─ downloader.py     # requests 下载 + 目录结构 + 断点续传
├─ parallel.py       # 多作品并发下载管理器
├─ store.py          # 通讯录（JSON）/ 历史（SQLite 增量写入，内存缓存）
├─ webdav.py         # WebDAV 增量上传（字节级进度）
├─ transfer.py       # 下载/上传进度、速度与任务面板（每个任务独立进度条）
├─ auto_upload.py    # 通讯录同步时的增量 WebDAV 上传队列
├─ author_assets.py  # 作者头像/简介存档
├─ theme.py          # 浅色主题
├─ resolver.js       # 页面注入探针（与 Android 版同一份）
├─ config.py         # 路径与常量
├─ tools/chromium/   # 便携 Chromium（可选）
├─ run_tests.py      # 测试入口（python run_tests.py）
├─ tests/            # 单元测试 + 离屏 GUI 冒烟
├─ test_core.py      # 手动集成自测（真实直链）
├─ requirements.txt
└─ README.md
```

`MainWindow` 由三块 mixin 组合而成：

```python
class MainWindow(WebdavMixin, ContactsSyncMixin, PlayerMixin, QWidget):
```

mixin 里的方法照常通过 `self.xxx` 访问主窗口的控件与状态（`store`、`dm`、
`upload_panel`、`status` …），由 `MainWindow.__init__` 统一创建；`Worker` 单独放在
`workers.py`，避免 mixin 反过来 import `app` 造成循环导入。每个 mixin 的类文档字符串
列出了它依赖的宿主属性。

运行时依赖 PySide6、Playwright 与 requests；数据（通讯录、历史、Cookie、登录态、
WebDAV 配置）保存在程序目录外的 `JingYingData`（或 `%LOCALAPPDATA%\JingYing`），
不上传任何内容。

## 界面更新（2026-10-31）

- **下载 / 上传分开显示**：传输区改为两个面板，各自有总进度条、实时速度（MB/s）
  和任务列表；每个下载/上传任务在列表里还有**自己的进度条、状态和百分比**。
  下载进度按**整个作品**统计：视频 / 图集图片 / 实况动图 / 背景音乐排成一条连续
  进度轴，0→100% 单调前进，不会每换一个文件就重走一遍；顶部总进度也按作品聚合。
  「传输列表」窗口同样按下载、上传分栏显示。
- **同步与下载并行**：抓完一位作者主页后，作品立即加入可追加的下载队列，同步
  立即继续抓下一位作者；下载在独立线程池执行，不再等一批作品下载完才继续同步。
- **只重试失败作者**：同步结束后若有作者读取失败，通讯录标题旁会出现
  「重试失败(N)」按钮；点击只重试这些作者，不再扫描全部通讯录；失败名单保存在
  `JingYingData/sync_failed.json`，重启程序后按钮仍然可用，成功重试后自动清除；
- **同步顺序随机**：每次「全部同步」都会随机打乱作者顺序，并尽量避开上一次的
  第一位作者，降低固定顺序触发风控/限流的概率；已下载作品仍按磁盘文件跳过；
- **多抖音号轮流同步**：账号 1～账号 5 各自使用独立的 Chromium 配置和 Cookie
  （`browser_session`/`browser_session_2`、`cookies.json`/`cookies_2.json`），
  可分别登录；多个账号都登录后，通讯录同步按作者轮流使用这些账号，降低单号
  被限流/安全验证的概率；只登录一个时保持原来的单账号行为；
- **同步发现记录**：状态栏会保留最近两位作者的「已发现 X 的作品 N 个」，同时显示
  当前抓取进度和下载完成数；下载进度覆盖状态时仍保留「正在同步 作者名 的作品」；
  若主页显示的作品总数更多，会标注「主页显示 M 个」，便于区分私密/受限作品和
  列表未加载完；
- **大账号抓取**：单作者上限提高到 5000 个，抓取超时提高到 10 分钟；每一页
  主页 API 响应都直接绑定到程序处理，避免一次滚动返回多页时只读到最后一页、
  前 50 个之后的作品被漏掉；接口偶尔提前返回 `has_more=0` 时，如果主页总数
  明显更多，会继续多滚动确认；作品不足 50 个的小作者读到总数后立即结束，
  不会为了“凑 50”空等；
- **文案补齐**：下载时会从作者资料补齐缺失的抖音号，标题为空时写入作品占位标题；
  旧文案里的“抖音号：未知”和空文案会在后台按历史记录修复一次；
- **WebDAV 目录也拍平**：远程同样是 `Videos/作者/作品`、`Music/作者/作品`，
  不再保留内层 `净影`；旧远程目录已迁移，上传记录同步改到新路径；
- **上传后清理本地**：WebDAV 区域新增开关，成功上传后只删除本地视频、图片和
  音乐，保留 `文案.txt`、历史记录、作者头像/简介和作者资料；
- **通讯录删除**：每位作者行有「删除」按钮，确认后只从通讯录移除作者，
  不会删除已下载作品、历史记录和作者资料；删除后保留当前加载页和滚动位置；
  同步过程中禁止删除，避免同步队列错乱；
- **加载更多不跳顶部**：通讯录和最近保存列表点「加载更多」后会保持原滚动位置，
  不再清空列表后回到最上面；
- **作者资料一起备份**：作者头像、简介和简介修改历史已移到
  `downloads/作者资料/`，随 WebDAV 的“上传全部”一起上传；通讯录同步时
  变更的作者资料也会进入自动上传队列；
- **UI 卡顿定位**：主线程超过 3 秒无心跳时会把主线程调用栈写进 `app.log`，
  便于定位“未响应几秒又恢复”的具体操作；
- **长时间同步稳定性**：解析完一位作者后通过事件循环排队再启动下一个解析线程，
  避免在 Worker.done 信号里递归创建 QThread；同步过程中不再每个作者都重建整个
  通讯录列表，改为结束/停止时刷新一次；
- **线程边界修复**：QThread/自动上传线程发出的信号连接 MainWindow 时显式使用
  `QueuedConnection`，下载完成回调不再在后台线程里直接操作 QWidget；自动上传
  不再在下载完成信号栈里同步 emit，避免 Qt/PySide 栈溢出；
- **主线程减负**：下载进度按作品聚合、每个作品约 8 次/秒节流；自动上传进度按
  百分比/200ms 节流；作者资料只做内存序列化（约 10ms）、真正的 open/写入/替换交给
  后台线程（每 10 秒交一次快照），不再在主线程等磁盘；
- **上传进度支持超过 2GB**：上传的字节类信号改用 64 位（`qint64`），累计上传超过
  2GB 时不再抛 `OverflowError`（Qt 的 `int` 只有 32 位），进度条会一直正常走；
- **历史存储改为 SQLite**：`history.db` 增量写入——新增作品只 INSERT、作者改名只
  UPDATE 受影响的少量行，不再把几万条历史整份重写（原来一次要 1 秒多）。首次启动
  自动把旧 `history.json` 导入并改名为 `history.json.migrated`；
- **同步收尾不卡界面**：作者头像改到后台线程下载；逐作品「下载日志」由后台线程
  攒批写盘；作品目录先扫一次，未下载的作品不再逐个 scandir；`sys.setswitchinterval(1ms)`
  降低并发线程对 UI 的抢占；
- **同步不再阻塞等线程**：下一个作者解析不再在主线程 `wait(3000)` 等旧线程退出；
  作者 saved_ids 只在批量 flush 时写盘，传输列表最多保留 120 行，避免同步时
  反复重写 authors.json 和无限插入任务行造成短暂卡死；
- 启动时启用 `faulthandler`，崩溃栈写入 `JingYingData/crash.log`；
- **同步时自动上传 WebDAV**：WebDAV 卡片新增「通讯录同步时自动上传新文件」开关
  （需先配置 WebDAV）。同步下载每个作品完成后，把视频/图集/音乐/文案加入独立上传
  队列，与通讯录解析、后续下载并行执行，不影响同步速度；已上传且未变化文件自动跳过。
- **云端低画质自动重下**（v1.5.0，默认关）：勾选「云端已有低画质时自动重下」后，
  同步遇到「本地已无媒体、云端有备份」的作品，会先读云端文件的真实分辨率——MP4 只
  用 `Range` 取 `moov/tkhd` 的几百 KB，不整包下载；tar 包取完立即删临时文件。
  只有低于本次解析结果才重下（短边比较、留 5% 容差），下载后覆盖上传，上传成功
  再删掉本地副本。上传记录里的字节数会先做粗筛（≥85% 视为同画质，连请求都不发），
  探测结果缓存 7 天，重复同步不会反复读云端。需同时开启上面的自动上传；图集不参与
  （签名模板图无法提像素）。**读不出云端分辨率时会保守地保留已有备份、不重下**，
  不会因为一次探测失败把整个已备份的库重下一遍；同步结束的汇总会列出跳过数量。
- **原始上传码流 / 原画质**（v1.6.0，默认关）：勾选「优先下载原始上传码流」后，
  在已登录的浏览器会话里用 `ratio=default` 回捞**未经重编码的视频码流**，按
  「原片体积 ÷ 最高转码档体积 ≥ 1.2」判定；通道未开放就自动回退最高转码档。
  这与下面 2026-11-08 章节讲的「阶梯里最高一档转码成品」不是一回事，详见文末专章。
- **线程数可调且会记住**：下载线程、上传线程分别设置，写入
  `JingYingData\settings.json`（或 `%LOCALAPPDATA%\JingYing\settings.json`）；
  关闭再打开对话框或重启程序都会保持上次的值。新线程数对下一次任务生效。
- **播放器文案浮层**：作者、发布时间、文案改为覆盖在画面上的半透明浮层，点击浮层

## 三块列表独立成窗（2026-11-04）

主窗口原来是一条长滚动页，结果卡片、批量、通讯录、WebDAV、传输、最近保存六张卡片
堆在一起，作者和作品一多就要一直往下滚。现在把三块「列表型」内容拆成独立窗口：

| 窗口 | 内容 | 打开方式 |
|---|---|---|
| 通讯录 | 作者列表、同步状态、同步日志 | 主界面「通讯录（N）」 |
| 传输 | 下载/上传两个面板、线程数、清空 | 主界面「传输」 |
| 最近保存 | 已下载作品列表、打开目录、清空 | 主界面「最近保存（N）」 |

通讯录的四个操作按钮（全部同步 / 重试失败 / 批量导入 / 导入 txt）留在**主窗口**，
不打开窗口就能发起同步；窗口里只放列表和状态，作者多的时候可以一直往下滚。

主窗口只保留解析、结果、批量、WebDAV 配置这几块，高度缩短了一半。

实现要点：

- 控件由窗口创建并持有，`MainWindow` 保留同名引用（`contact_list` / `history_list` /
  `download_panel` / `transfer_dl_combo` …）。原来 200 多处 `self.xxx` 调用一行没改。
- 窗口关闭只是隐藏（不设 `WA_DeleteOnClose`），后台同步/上传线程仍能安全更新控件，
  再次打开时内容还在。
- 去掉了通讯录的「收起/展开」——独立窗口里列表直接铺满，不再需要折叠。
- 原来的 `TransferDialog`（复制一份面板再同步）删掉了：面板只有一份，就是传输窗口里
  那一份，线程数下拉框也直接是主窗口的设置来源。
- 新增 1 个用例覆盖三个窗口的打开/隐藏与控件归属，共 100 个用例。

## 代码结构拆分（2026-11-04）

`app.py` 原来 3540 行、`MainWindow` 一个类 142 个方法，改一处要在几千行里翻。
这次按「能独立讲清楚的一块业务」拆出去，**方法体原样搬运，不改逻辑**：

| 模块 | 行数 | 内容 |
|---|---|---|
| `app.py` | 2241 | 主窗口骨架、单条解析、批量、历史列表、登录、UI 搭建 |
| `contacts_sync.py` | 616 | 同步状态机、作者目录改名、已下载判断、失败重试 |
| `webdav_panel.py` | 577 | 上传配置、增量上传、进度、上传记录、上传后清理 |
| `workers.py` | 36 | 后台 `QThread`（各 mixin 共用） |

- 采用 mixin 而不是独立控制器：这些方法大量读写主窗口状态（`self.store`、
  `self.dm`、`self.upload_panel`…），拆成独立类要么传一堆参数，要么加一层转发，
  反而更难读。mixin 保持 `self.xxx` 原样，调用点零改动。
- `Worker` 抽到 `workers.py`，否则 mixin 需要 `from app import Worker`，形成循环导入。
- `UploadBridge` 跟着 WebDAV 一起搬到 `webdav_panel.py`。
- 搬运用脚本按方法边界切分，并用 `ast` 逐方法比对：**142 个方法、方法体零差异**。
- 新增 1 个回归用例覆盖之前没有测试的播放器入口（`_open_player` → 后台组装 feed →
  打开 `PlayerWindow`），共 99 个用例。

### 同时修复：解析/同步全部失败

排查「读取总是失败」时发现是两个环境问题叠在一起，代码只改了浏览器选择这一处：

1. 运行程序的 Python 里没有 `playwright`，`resolve_profile` 一进来就抛
   `No module named 'playwright'`，347 位作者挨个失败两次。装回 `playwright` 解决。
2. `tools/chromium/chrome-win/` 这个便携 Chromium 缺 `chrome_crashpad_handler.exe`，
   启动时报 `crash server failed to launch, self-terminating` 直接退出。
   `config.resolve_chrome()` 新增 `_browser_usable()`：目录里有 `chrome.dll` 却没有
   crashpad handler 就跳过，自动退到系统 Chrome / Edge。

修完后实测：单个作品解析出标题/作者/抖音号/播放地址/音乐地址；主页抓取
「萱啊xuan」读到 103 个作品（98 视频 + 5 图集），与主页显示总数一致。

## 启动与同步性能（2026-11-03 优化）

本机实测数据规模：历史 17,152 条（当时 `history.json` 21 MB，现为 `history.db`）、通讯录 347 位作者、
上传记录 78,533 条（`webdav_uploaded.json` 10 MB）。

- **启动不再白屏**：`MainWindow.__init__` 里还留着一次同步的 `_normalize_file_times()`，
  和后台 maintenance 重复执行，1.7 万条历史要 stat 7 万多次路径（4.6 s）。
  删除同步调用后，窗口先出现、整理在后台跑。
  **同机交替 A/B：6.44 s → 0.50 s（约 13 倍）。**
- **历史列表延后渲染**：`_render_history()` 首次调用要解析 21 MB JSON（1~2 s）。
  改为先显示「正在载入历史记录…」，后台线程读完历史立即通知界面渲染前 80 条，
  不用等后续扫盘/修时间跑完。整理失败也会渲染，不会一直停在「载入中」。
- **文件时间修真正在变便宜**：历史条数 + 最新 `saved_at` 没变时直接跳过扫盘；
  每条记录先 `isdir` 判断作品目录，目录不存在就跳过整条（已删除的作品不再逐个
  stat）；用一次 `os.stat` 代替 `exists` + `getmtime`，系统调用减半。
- **配置导入不再解析历史**：`config._flatten_history_paths()` 每次启动都重新解析
  21 MB 历史来检查旧路径。迁移成功后写 `JingYingData/history_paths_flattened_v1`
  标记，之后启动直接跳过。
- **上传记录缓存**：`_load_webdav_state()` 每次刷新状态栏都重新解析 10 MB JSON。
  改为按（服务器, 远程根目录）缓存，配置变更时自动失效；启动时状态栏先不显示数量，
  由后台线程读完再补。
- **历史写入去重不再 O(n)**：`Store.add_history()` 原来每保存一个作品都全量重建列表。
  改为维护 `aweme_id` 索引，重复才做一次 `list.remove`。
  实测连续写入 500 条：**2.32 s → 0.011 s（约 200 倍）**。
- **已下载判断换 scandir**：同步时每个作品都要 glob 一次目录，改用 `os.scandir`
  前缀匹配，单次快 2~3 倍（上千个作品的同步少几百毫秒主线程占用）。
- **传输列表空转归零**：`TransferPanel.sync_from()` 加了内容指纹，400 ms 定时刷新
  在任务状态没变时直接返回，不再每帧重设上百个控件。
- **同步结束后释放队列**：`_dl_jobs` / `_dl_authors` 在同步完成后清空，
  大账号（上万作品）不会一直把 `MediaInfo` 挂在内存里。

### 同时修复的问题

- **同步失败会跳作者**：`_sync_failed()` 里 `QTimer.singleShot(400, self._sync_next)`
  写了两遍，失败一次会把同步队列连推两位（跳过一位作者、并让两个浏览器任务抢锁）。
  改为只排一次。
- **无效的浏览器调用**：`parser.py` 兜底分支里 `page.evaluate(...)` 的返回值从未使用，
  每次解析失败都白跑一次页面脚本，已删除。
- 清理 pyflakes 报出的未使用导入/变量（`QIcon`、`QGridLayout`、`QSplitter`、
  `auto_upload` 的 `webdav` 等），`app.py` / `store.py` / `parser.py` / `player.py` /
  `transfer.py` / `config.py` 现在零告警。
- 新增 3 个回归用例：历史索引在 merge/save/clear 后仍正确、启动占位→整理后渲染、
  整理失败仍渲染历史（共 97 个用例）。

## 缺陷修复与性能（2026-11-07 优化）

本轮以「先修真实缺陷、再谈性能」为原则：先把代码读一遍做静态审计，把结论落到
可复现的用例上，再逐条修。`python run_tests.py` 从 109 个用例增加到 **129 个，全部通过**
（2026-11-08 的 tar 改造与原画质下载之后是 145 个；本机约 5~7 分钟；新增用例覆盖下文的跨轮次回调、
空 id 历史、Cookie 过期、临时文件清理、文件名保留字、日志后台写盘等回归点）。

### 停止同步后立刻重开：数据错位

- **下载回调跨轮次错位**：`parallel.DownloadManager.begin()` 现在会换一个轮次号
  （generation）。上一轮还在跑的任务（`requests` 读超时 60 秒，停止后最多还能再跑
  一分钟）带着旧索引回来时整体丢弃，不再写进新一轮的 `_dl_jobs`：以前会把作品 A 的
  下载结果写成作品 B 的历史、让 `_dl_done` 虚增并触发同步提前收尾。
- **同步 worker 迟到信号**：`contacts_sync` 增加 `_sync_generation`。停止后立刻重新
  同步时，上一轮 worker 迟到的 `finished` 不再 pop 掉新一轮同一槽位正在跑的作者
  （那会让「作者资料抓取完」提前为真，整轮静默丢作者）。
- **索引越界不再崩进程**：`_dl_item_done/_dl_item_error/_dl_item_progress/_dl_item_started`
  统一走 `_dl_job(index)` 守卫。以前 `self._dl_jobs[index][0]` 越界抛 `IndexError`，
  PySide6 新版会直接终止进程。
- **传输列表行 key**：改用「轮次号 + 索引」，不再用 `id(self._dl_jobs)`——每轮同步都会
  换新 list，CPython 很容易把同一地址复用给下一个 list，新任务就写进上一轮的行里。

### 账号与登录状态

- **账号归属**：`_sync_profile_done` 的 lambda 以前丢了 `account_index`。账号 3 解析成功
  后如果抛异常，会按默认值 0 去改「账号1」的登录状态，把真正失效的账号留在可用槽位里。
- **登录失效只影响真正在用的账号**：只有 `account_index in self._sync_slots` 时才写
  `login_state.json` 并摘掉槽位。
- **过期 Cookie 不再算已登录**：`_cookie_alive()` 按 `expires` 过滤。以前只看 Cookie
  名字，服务端会话过期后界面一直显示「已登录」，同步却整轮报「需要登录」，重启又变回来。
- **Cookie 迁移只做一次**：新增 `cookie_migrate_v1` 标记。没登录过的用户以前每次启动
  都会白开两只浏览器去迁移 Cookie。
- **没装浏览器时直接说清楚**：`_parse` / 「只保存音乐」/ 「全部同步」在 `CHROME_PATH`
  为空时给出可读提示，而不是让 Playwright 抛 `Executable doesn't exist` 或给每位作者
  各起一次注定失败的浏览器。
- **登录中不再点解析**：登录窗口开着、或正在检查登录状态时，解析入口直接拦下并说明原因
  （登录与单条解析共用账号1的浏览器目录，锁的等待上限是 15 分钟）。

### 浏览器资源

- **context 统一收尾**：`_serialized_browser` 装饰器现在用 `contextvars` 登记本次调用
  创建的所有 context，退出时全部关闭。`resolve_video` 以前完全没有 `_close_context`，
  `resolve_profile` 只覆盖了部分分支——任何异常路径（goto 超时、页面跳转、字段解析失败）
  都会留下没关掉的持久化 Chromium：Cookie 不落盘、profile 锁残留，下次启动命中
  `ProcessSingleton` 后被悄悄换成临时配置目录。
- **临时配置目录随 context 删除**：`mkdtemp` 出来的 `jy_profile_*` / `jy_cookie_*`
  以前只增不减；现在关闭时删除，后台维护线程再兜底清两天前的残留（每次最多 12 个）。
  Playwright 自己建的 `playwright_chromiumdev_profile-*` 也在清理范围内——本机
  `JingYingData/tmp` 里实测堆了 **66 个、306 MB**（都是浏览器没被正常关闭留下的）。
- **目录锁按真实实参取**：`_bound_session_dir()` 用 `inspect.signature().bind_partial()`
  取 `session_dir`。`resolve_profile_sync` / `check_login_status_sync` 都是位置传参，
  以前一律锁到账号1 的目录：不同账号白白串行，一次登录检查还可能被别的浏览器拖到超时。

### 启动与磁盘

- **`config` import 期不再能拦住启动**：`_pick_dir` 连兜底目录都建不出来时退到系统临时
  目录（以前抛 `OSError`，双击 exe 无窗口、无日志地退出）；`os.listdir` 加保护；
  `_migrate_flat_downloads()` 整体 try。
- **作者资料迁移加标记**：`author_assets_migrated_v1`。以前每次启动都要读一遍 700KB 的
  通讯录，再对每位作者的头像做 `isfile`（本机 291 个头像目录 ≈ 上千次系统调用）。
- **清理残留临时文件**：启动时删除一小时前的 `名字.<pid>.<tid>.tmp`（原子写入被强杀时
  `finally` 跑不到）。本机实测一次清掉 **47 MB** 孤儿文件。
- **同步日志也走后台写**：新增 `line_log.py`，`sync_log` 与 `download_log` 共用同一套
  队列 + 攒批写盘。以前每位作者都在主线程 open/append/close 一次，几百位作者就是几百次
  主线程磁盘写；日志窗口把「队列里还没落盘的行」也算作有新内容，刷新不丢。
- **批量导入作者只落盘一次**：循环里 `flush=False`，结束统一 `flush(block=True)`。
  实测导入 300 位作者（通讯录已有 347 位）：**4.55 s → 0.086 s，约 53 倍**。
- **加入通讯录的头像改后台下载**：以前在主线程 `requests.get(timeout=30)`，网络慢时
  点一下按钮界面假死半分钟（同步流程本来就是后台下载）。

### 界面与文件名

- **清空历史后「加载更多」不再残留**：空列表分支提前 `return`，跳过了按钮显隐。
- **关闭主窗口会一起关播放器**：播放器是没有 parent 的顶层窗口，不关它进程不退出，
  而此时 `store` 已经 close，播放器里再点「同步」会往已关闭的写线程提交数据。
- **Windows 文件名保留字**：`sanitize_segment()` 处理 `CON/NUL/COM1…`、结尾的点与空格、
  `.`/`..`。昵称正好叫 `CON` 的作者以前 `makedirs` 必失败，而「已下载」判断恒为 False，
  于是每轮同步都重下一遍；`download_work()` 另外拒收会跳出下载根目录的目录名。
- **空 `aweme_id` 的历史各占一行**：`_backfill_seqs()` 以前把所有空 id 映射到同一个 seq，
  之后 `update_history_items()` 反复 UPDATE 同一行——最后一条覆盖前面全部，其余条目在
  库里永远停在旧值（作者改名后路径没落库，下次启动就提示「文件可能已被移动或删除」）。
- **退出时不再死等**：`Store.close()` 改成带 2 秒超时的取锁（后台线程被 `terminate()`
  停在锁里时不再永久阻塞，进程残留）。

### 三处脚本与配置的编码损坏

- `安装依赖.bat` / `运行测试.bat` / `.gitignore` / `requirements.txt` 之前是 **GBK 字节 +
  `chcp 65001`**：中文全是乱码，而且坏字节把换行吞了——`运行测试.bat` 里的
  `echo 测试失败….) else (` 被执行成一行，语法直接坏掉；`安装依赖.bat` 的 `pause`、
  `exit /b 1` 也被粘进上一行 `echo`。现在三个 bat 统一 **GBK + `chcp 936`**（本机活动代码页
  936，见 `chcp`），`requirements.txt` / `.gitignore` 恢复成正常 UTF-8 注释。

### 本轮没做的事（已知短板）

- **关闭窗口仍会对卡在网络上的 `QThread` 调 `terminate()`**：Qt 层面没有安全的强制中断
  手段。现在只是让 `Store.close()` 不会因此永久阻塞；彻底方案是每个任务线程独占一个
  SQLite 连接、并用 `stop_event` 而不是杀线程。
- **「加载更多」仍是清空重建**：历史/通讯录每次 `clear()` 后重加 `页数×80`（作者 `×40`）
  行。条目特别多时仍有毫秒级开销，改 `QAbstractListModel` 才能从根上解决。
- **登录等待仍是 `processEvents()+sleep(0.1)` 自旋**，并且用 10 秒超时判断「用户点了我已
  完成登录」。改成 `QEventLoop` + 定时器更稳，但要一起改登录状态机，风险大于收益，留待
  下次。
- **`caption_metadata_fixed_v1` 无论修没修都会写**：首次启动时如果通讯录还是空的，这批
  旧文案就永久放弃了修复。因为该检查要读上万个 `文案.txt`，故意保持「只做一次」。

## 每个作品一个 tar（2026-11-08）

**新规则**：下载好一个作品后，把该作品的所有文件（视频 / 图集图片 / 实况动图 /
背景音乐 / 文案.txt）收进一个文件夹，打成 `<作品id>.tar`，散文件随即删除。

```text
Videos/抖音名_抖音号/7525082444551310602.tar
        └─ 作者名_文案_发布时间/
             视频.mp4 · 音乐.mp3 · 文案.txt        （图集作品是 图片_01.jpg / 动图_01.mp4…）
```

实现要点：

- **先临时目录、再原子打包**：文件先落到 `JingYingData/tmp` 里的临时文件夹，
  下载完调用 `archive.pack()` 打成 `.part` 再 `os.replace` 成正式包——中途取消、
  断网、断电都不会留下半个 tar 被当成「已下载」。临时目录在 `finally` 里清理，
  取消和异常也不会留散文件。
- **包内保留作品文件夹**：tar 的顶层目录仍是「作者名_文案_发布时间」，
  手动解压不会把一堆 `图片_01.jpg` 散在当前目录。
- **文件名**：用 `<作品id>.tar`；拿不到作品 ID 时退回作品文件夹名，避免所有包撞名。
- **播放器按需解包**：信息流里带 `archive` 的条目在**切到那一条时**才解包到
  `JingYingData/tmp/jy_play_*`（同一个包解一次，来回切换不重复解压），
  播放器关闭时整目录删除——不会为了播放把整个信息流解压一遍。
- **已下载判断**：同步时先扫一次作者目录，看 `<作品id>.tar` 在不在；0 字节的空包
  不算已下载。旧版的作品文件夹仍然认，已经下过的老作品不会被重下。
- **历史与磁盘重建**：`<作品id>.tar` 会作为作品记录进历史（包里的 `文案.txt`
  用于还原作者、抖音号、完整文案和发布时间）；旧版散文件目录也仍然能识别。
  **本轮只对新下载的作品生效**，不回填历史作品。
- **WebDAV**：tar 就是上传的那份文件；「上传后清理本地」把 `.tar` 也算作媒体，
  上传成功后一起清掉（文案在包内，服务端已有备份）。
- **测试**：新增 `tests/test_archive.py`（打包 / 成员顺序 / 解包缓存 / 坏包）和
  播放器解包用例，下载器用例改成断言 tar 结构与「散文件已清理」；
  `python run_tests.py` 现在共 **145 个用例**。

## 原画质下载（2026-11-08）

以前只从 `play_addr` / `play_addr_h264` / `play_addr_265` 这三个兜底地址里挑，等于放弃了
清晰度阶梯，最高只能拿到 1080p。现在改成在 `video.bit_rate` 阶梯里按「分辨率优先」挑：

```text
选择顺序：分辨率(宽×高) 最大  →  完整 mp4（不是 dash 分段）  →  data_size 最大
          →  bit_rate 最大  →  同条件下优先 H.264
```

以本机缓存的真实样本（`tools/dyprobe/detail-7525082444551310602.json`）为例：

| 来源 | 分辨率 | 体积 | 编码 |
|---|---|---|---|
| `bit_rate: adapt_lowest_4_1` (mp4) | **2340×2160** | 59.9 MB | H.265 ← 选中 |
| `bit_rate: adapt_lowest_4_1` (dash) | 2340×2160 | 56.0 MB | H.265 |
| `bit_rate: normal_1080_0` | 1170×1080 | 56.0 MB | H.264 |
| `bit_rate: adapt_lowest_1440_1` | 1560×1440 | 40.5 MB | H.265 |
| `play_addr_265` | 1560×1440 | 40.5 MB | H.265 |
| `play_addr` / `play_addr_h264` | 780×720 | 40.2 MB | H.264 |

改动点：

- `models._stream_candidates()` 把 `bit_rate` 每一项的 `play_addr`（分辨率、`data_size`
  都在里面）连同三个兜底地址一起列成候选；分辨率/体积字段缺失时退回外层条目取。
- `models._rank_stream()` 排序键＝`(分辨率, 是否完整 mp4, 码率, 体积, 是否 H.265)`。
  码率排在体积前面：「原画」的判定标准是同分辨率里码率最高那档，而 `bit_rate`
  条目偶尔缺 `data_size`，按体积比较会把它当成 0，反而选中更低码率的档。
- 结果卡片（`app._show_result`）会显示实际选中的清晰度；`info.quality` 由原来的
  `gear_name` 改成人能看懂的「原画 2160p · H.265」。
- 实况图（动图）走同一套挑选逻辑（`models._video_url`）。
- 图集图片不涉及清晰度阶梯，仍取 `url_list` 第一条。

**注意**：原画基本都是 **H.265 / HEVC**。本机 Qt 6.12 的 FFmpeg 插件可以解码，内置播放器
正常播放；但如果你把文件拿到很老的播放器/设备上，个别会不支持 HEVC——需要的话，把
`_rank_stream` 里的 `是否 H.264` 提到分辨率之前即可退回「优先通用编码」。
另外原画的文件明显更大（示例样本 40 MB → 57 MB），下载耗时和磁盘占用都会相应增加。

`python run_tests.py` 中新增 5 个用例覆盖：原画阶梯选择、同分辨率优先完整 mp4、
同分辨率比体积、无阶梯时回退、实况图取最高画质。

## WebDAV 上传全部失败（2026-11-10 修复）

现象：同步时自动上传、或手动点「上传全部」，所有文件都失败，界面只有「失败 N 个」，
日志里是一串 `MKCOL 净影 -> HTTP 409`。

原因有两层：

1. 123 云盘 WebDAV 创建目录时会返回 409（当时连顶层 `净影` 都建不出来）。旧代码把
   409/301 一律当成「目录已存在/创建成功」写进缓存，父目录实际不存在，子目录和
   文件上传自然全失败，而且本次运行不会再重试，于是一个临时故障放大成「全部失败」。
2. `AutoUploader` 把上传异常整个吞掉，只统计失败个数，日志里没有任何原因。

修复：

- `ensure_dir` 只有 MKCOL 200/201/204/405 才认成功；409/423/5xx 重试后还用
  PROPFIND 核实，确认存在才写缓存，否则抛出「创建远程目录失败 …」；失败目录缓存
  20 秒快速失败，服务端恢复后自动继续。
- `upload_file` 遇到 PUT 409 会清掉父目录缓存、重建后重传一次。
- 「测试连接」会真的检查远程根目录；手动上传开始前先 `ensure_root()`。
- 自动上传新增 `file_failed` 信号，状态栏/tooltip 显示第一条真实错误，同时写入
  `app.log`。
- 手动「上传全部」只扫描 `净影`、`Videos`、`Music`、`作者资料`。此前开发版的上传根
  是用户主目录，会把桌面、文档、AppData 一起遍历（既慢又可能上传私人文件）。

### 远程出现「净影/净影」（2026-11-11 修复）

远程根目录叫 `净影`，本地作品相对路径也以 `净影/` 开头，`_url()` 又拼了一次根目录，
于是变成 `净影/净影/作者/...`。现在相对路径已经带根目录名时不再重复拼接；已有的
80 个作者目录已用 WebDAV MOVE 从 `净影/净影/` 迁到 `净影/`，空的 `净影/净影` 已删除。
上传记录 key 本来就是 `净影/作者/...`，无需改动。

## 稳定性与一致性（2026-11-12 优化）

本轮先做静态审计，再按「能复现 → 修 → 补用例」逐条处理。改动前备份在
`.backup_opt/before_20261112/`；新增 18 个回归用例，`python run_tests.py`
共 175 个用例全部通过（改动前基线 157 个用例里有 1 个失败）；同日第二轮的
协作式退出再新增 13 个用例，最终 `python run_tests.py` 共 188 个用例全部通过。

### 修复的功能缺陷

- **自检入口与保存结构脱节**：`python app.py --selftest` 的第 4 项仍按 2026-11-08
  的 tar 结构断言（`archive_path` 现在是空串，`getsize("")` 必然抛异常），而且只把
  `DOWNLOAD_BASE` 指向临时目录，作品其实会真的下到用户的 `净影/`。现在改成检查
  同一个作品文件夹里的视频 / 音乐 / 文案，并把 `SAVE_ROOT` 一起重定向。
- **双击「最近保存」打开别人的作品**：列表渲染之后后台再插入新作品，行号会整体
  错位。改用 `QListWidgetItem` 的 UserRole 里本来就存着的 `aweme_id` 反查，行号
  只兜底没有 id 的老记录。
- **日志窗口能把界面永久冻住**：`line_log.load()` 在主线程做无超时的
  `Queue.join()`，每 1.2 秒一次；写盘线程一旦卡在被占用的文件上，整个 GUI 就
  再也不响应。现在 `flush(timeout=0.5)` 限时等待，写盘锁也改成限时获取，拿不到
  就跳过本次刷新（返回 `None`，窗口保留已有内容，不会闪成空）；写盘失败也会
  写进 `app.log`。
- **「上传全部」先传音乐**：排序键还硬编码 `Videos/`，新作品在 `净影/` 里，中文名
  按字符串排会落到最后。现在优先级由 `UPLOAD_DIRS` 推导，目录再改名也不会脱节。
- **一处失效的回归用例**：`_fake_download` 仍把作品写进「作者_文案_时间」目录，
  与真实 `work_dir()` 的作品 id 目录不一致，导致「上传后删除本地媒体」的检查恒真；
  同一用例还把 patcher 当成 mock 取 `call_count`。两处对齐后，该用例才真正验证
  「不会重复下载」。

### 资源与性能

- **启动探针不再堆积**：写权限探针以前叫 `.write_probe_<pid>_<时间>` 且从不删除
  （本机数据目录实测 40 多个）。改成固定名字覆盖写（仍不删，避免某些环境删文件
  卡住启动），旧格式由启动清理回收；`crash-<pid>.log` 也按「空文件 / 超过 7 天」回收。
- **自动上传状态落盘节流**：以前每成功一个文件就把约 10 MB 的上传记录全量重写，
  同步上千作品是 O(n²) 磁盘写。现在与手动上传一致：20 秒节流 + 收尾强制落盘。
- **WebDAV 连接池回收**：`WebDAVClient.close()` 统一关闭 thread-local 的 Session，
  在测试连接 / 手动上传 / 自动上传结束时调用。
- **解包缓存不再认半个目录**：`extract()` 全部文件 move 完才写 `.complete`，缓存
  命中同时校验标记；老缓存文件齐全时自动补标记，不重复解包。
- **`CreateFileW` 句柄判断修正**：以前没声明 `restype`，64 位 HANDLE 被截成 32 位，
  `INVALID_HANDLE_VALUE` 判断恒为假，失败会拿 -1 去 `SetFileTime` 且异常被吞掉。
  现在声明 argtypes/restype、正确判断、句柄用 `finally` 关闭。
- **批量导入作者去重**：`extract_all_sec_uids` 的 list 线性查找换成 set，O(n²) → O(n)。

### 后台线程的协作式退出（同日第二轮）

改动前备份在 `.backup_opt/before_20261112_stopevent/`。

- **`Worker` 自带停止信号**：`workers.Worker` 现在持有 `threading.Event`。任务只要
  在签名里声明 `cancel_event`（或 `stop_event`）就会收到它；`request_stop()` 同时
  置位 Event 和 Qt 的 `requestInterruption()`。在检查点主动中断的任务不会再 emit
  `failed`，关窗时不会弹「下载失败」对话框；真实异常仍照常报错。
- **下载侧贯通**：单作品下载、单独下载音乐、封面下载都把 `cancel_event` 传给
  `downloader`（chunk 循环里本来就有检查）。取消时 `with open(part, "ab")` 正常
  关闭，`.part` 留作续传；封面没有续传语义，取消时删掉半截 `.part`。
- **解析侧贯通**：`resolve_video` / `resolve_profile` 新增 `cancel_event`，在页面
  打开后、轮询循环开头、滚动等待后检查，置位抛 `ParseCancelled`，让
  `_serialized_browser` 的 `finally` 照常关掉 Playwright context、释放配置目录锁。
  等这把锁也从「一次阻塞 900 秒」改成 0.2 秒间歇获取，关窗时能立刻放弃等待。
- **`closeEvent` 不再无差别强杀**：先对所有运行中的 Worker 发停止通知，等 3 秒；
  只对「已通知 + 已等待仍无响应」的线程保留 `terminate()` 并写 WARNING 日志。
  登录用的独立 `threading.Thread` 也会被置位，避免关窗后浏览器继续挂着。
- 新增 `tests/test_stop_event.py`（13 个用例）：信号注入、`finally` 确实执行、
  取消静默、等锁可中断、关窗不强杀、无响应线程仍走兜底。

**边界**：卡在 `page.goto()` / `requests` 连接等待里的线程看不到 flag，最长仍受
Playwright 20 秒默认超时约束，极端情况还是会走兜底强杀；这与改动前「3 秒一到
全部强杀」不同，但还不是零强杀。

### 本轮仍然没动

- 「加载更多」清空重建、登录等待 `processEvents()+sleep` 自旋、
  `caption_metadata_fixed_v1` 一次性标记保持原样，改动面比收益大。

## 已知限制

- **主页列表需要登录**：抖音未登录不返回作品列表，登录由用户在本机浏览器完成。
- **需要较新 Chromium**：抖音网页依赖现代 JS；建议 Chrome 120+。
- **下载在程序进程内**：批量/同步时请保持程序运行；关闭窗口会取消未完成任务，
  已下载部分保留为 `.part`，下次解析会尝试续传。
- **直链有时效**：过期后重新解析即可。
- **音频目录**：背景音乐按系统惯例放 `Music/作者`，与 `Videos/作者` 同名对应。
- 私密作品、付费内容、直播、部分地区限制内容无法下载。

## 原始上传码流 / 原画质（2026-11-12，v1.6.0）

> 依据《抖音「原画质」获取实现规范》(2026-11)。**仅用于本人作品或已获授权内容**
> 的归档与画质分析；不破解签名、不绕过登录与权限、不用于批量抓取他人作品。

### 先分清三种「原画质」

| 概念 | 定义 | 能否拿到 |
|---|---|---|
| 逐字节母版 | 上传时那个文件，SHA-256 一致 | ❌ 公开渠道拿不到 |
| **原始上传码流** | 平台保留的原片，视频码流未经重编码 | ✅ **本版目标**，部分作品可以 |
| 转码档 / 无水印版 | CDN 上的多档成品，已重编码 | ✅ 一定能拿到，但不是原片 |

以前那个「原画质下载（2026-11-08）」章节讲的是**第三种里最高的一档**。
把 `playwm` 换成 `play` 只是换 CDN 路径，编码没有任何变化。即使本版判定为
`original`，也必须说明：**视频码流未经重编码，但容器与元数据被平台用 FFmpeg
重封装过，不等于上传时那个文件的字节副本。** 需要 SHA-256 对齐请回头找原文件。

### 程序里怎么用

1. 先「登录抖音」建立登录态（Cookie 落在 `JingYingData/cookies.json`）。
2. 在 WebDAV 卡片勾选 **「优先下载原始上传码流（原画质）」**（默认关）。
   每个作品会多 2 次请求并加 1.2~3.0 秒节流，原片体积可能是转码档的 20 倍，
   批量同步会明显变慢，所以默认不开。
3. 正常解析 / 下载即可。结果卡片的画质标签会显示「原始码流 78.5MB · 24.1x」；
   原片通道未开放时标签回到「原画 1080p」并自动使用最高转码档。

### 实现要点

- **不实现签名**：需要 `a_bogus` / `msToken` 的 `aweme/detail` 请求由真实作品页
  的 JS 代发（复用 `resolver.js` 的 `__JY_STATE__.detail`）；play 端点在已登录的
  浏览器上下文内发出，Cookie 天然正确。平台换签名算法时本实现不用改。
- **回捞**：`video.play_addr.uri` 才是 `video_id`（不是 `aweme_id`）→
  `GET /aweme/v1/play/?video_id=…&ratio=default&line=0&improve_bitrate=1&watermark=0`
  ，`max_redirects=0` 只读 `Location`，**不把 80 MB 视频拉一遍**；`Location` 缺失
  时退回页面内 `fetch` 并立即取消响应体 → `HEAD` 取体积与类型。实测部分腾讯 COS
  节点对 `HEAD` 返回 404 `application/xml`，此时降级为**只读 1 KB 的 Range GET**，
  从 `Content-Range` 读总长度再判定（不会误把 1024 字节当文件体积）。
- **选档与判定**：最高转码档按 `play_addr.data_size` **降序**取（实测 540p 档
  4.99 MB 比 720p 档 4.18 MB 还大，按分辨率排会取错）；`factor = 原流体积 /
  最高档体积`，`>= 1.2` 判 `original`，否则 `transcoded`。三个实测基线：
  24.2x / 0.43x / 3.72x，中间没有模糊地带。
- **拿不到是正常结果**：蓝V、投流作品等原片通道不开放，换 `ratio` 也没用，
  程序会回退最高转码档，不报错、不死循环重试。
- **直链有时效**：单条解析的结果缓存 120 秒；批量同步「先解析全部作者、再下载」
  会隔很久，下载前会按 `video_id` 即时重取（独立 Chromium profile + 已保存
  Cookie + 首页预热）。直链下载失败会清缓存重取一次，仍失败则回退。
- **软失效断言**：`aweme_id` 非空；`desc` 与 `author` 不同时为空；`play_addr.uri`
  与 `bit_rate` 存在；CDN `Content-Length > 100 KB` 且 `Content-Type: video/*`。
  命中人机校验 / 未登录时明确报错而不返回坏数据。任何回捞失败只记日志，
  **不会让作品下载失败**。
- **落盘校验**：`original_stream.inspect_mp4()` 不需要 ffprobe，读 `ftyp` 品牌、
  遍历所有 `trak` 找 `stsd` 编码 tag（`avc1` / `hvc1` / `av01`）、宽高、`mvhd`
  时长与平均码率；元数据（Apple 设备信息、拍摄时间戳）只在 `moov` 范围内扫描，
  避免 `mdat` 随机字节造成假命中。`Lavf` 标记原片和转码档都有，不能单独当判据。

### 命令行（推荐用于验证与定时巡检）

```bash
python tools/original_cli.py login-status                   # 本地登录 Cookie 是否在
python tools/original_cli.py probe <你的作品链接或ID>        # 只读：不发下载请求，打印 factor/verdict
python tools/original_cli.py download <你的作品链接或ID> --out D:\归档
python tools/original_cli.py check D:\归档\视频.mp4           # 编码/元数据/码率结构判定
python tools/original_cli.py regress                        # 离线回归，失败返回非零退出码
```

CLI 面向**源码运行**（打包版请用界面开关）；`probe` 只发 `play` + `HEAD`
两个请求，适合先确认通道是否开放；`download` 会把结果写成
`original_probe.json` 便于复核。`regress` 不需要网络，可以直接挂
每日定时任务——抖音的失效大多是静默的（HTTP 200 但字段被裁剪），当天就该发现。
